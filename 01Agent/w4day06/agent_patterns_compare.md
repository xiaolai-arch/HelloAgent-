# Agent 四大模式对比笔记（W4 Day6）

> 对应任务：学习 Plan-and-Execute / Reflection / Multi-Agent 模式；
> 整理"Agent 四大模式对比表"；思考"哪些场景适合哪种模式"。
> ReAct 的代码实证见 `../w4day01/react_loop_demo.py`（手写循环 + 完整轨迹）；
> 本文聚焦另外三个模式 + 全家福对比。

---

## 0. 全家福：一张表看完四大模式

| 模式 | 一句话 | 控制流 | 优点 | 缺点 | 适合 | 不适合 |
|---|---|---|---|---|---|---|
| **ReAct** | 走一步看一步 | Thought→Action→Observation 循环 | 简单、灵活、每步可解释 | 误差累积、上下文越滚越长、易打转 | 工具少（几个以内）、路径不确定的探索 | 步骤强依赖的复杂任务、高质量写作 |
| **Plan-and-Execute** | 先列清单再干活 | Plan → 逐步 Execute → 必要时 Re-plan | 全局视野、步骤可并行、不轻易跑偏 | 初始计划定上限；环境突变时计划过时 | 结构清晰的多步任务（调研+写报告） | 探索式、连目标都不清晰的场景 |
| **Reflection** | 写完自己批一遍 | Draft → Critique → Revise 循环 | 写作/代码质量显著提升 | 每轮都是真金白银的 token 和延迟；可能过度打磨或死循环 | 质量可迭代打磨的任务（文案、代码 review） | 一次性事实查询、延迟敏感场景 |
| **Multi-Agent** | 开会式分工协作 | 多角色/多子系统消息传递 | 分工并行、上下文隔离、互相制衡 | 通信开销、错误级联、调试困难 | 子任务天然独立可并行（多代码库、多源调研） | 单 Agent 能干的活（复杂度是成本） |

## 1. ReAct：一切的起点（复习 + 指针）

- 循环：Thought（缺什么）→ Action（调工具）→ Observation（真实事实回填）→ …→ Final Answer。
- Day1 实测结论：协议可用但脆弱（文本协议出现格式违规，需要重试提示）；
  Observation 是防幻觉的锚；上下文滚动成本是二次曲线。
- **其他三个模式都建立在 ReAct 之上**：Plan-and-Execute 的"Execute 一步"通常
  就是一个 ReAct 循环；Reflection 的执行者也是它；Multi-Agent 的每个 Agent
  内部还是它。

---

## 2. Plan-and-Execute：把"想清楚"和"动手"分开

```text
用户目标
   │
   ▼
Planner（一次性输出完整步骤清单 [1,2,3...]，可不调用工具、只需推理）
   │
   ▼
Executor（逐步执行每一步；每步通常是一个 ReAct 微循环）
   │
   ├─ 步骤失败或新信息推翻前提 ──▶ Re-plan（重新生成剩余计划）
   ▼
汇总产出
```

- **与 ReAct 的本质区别**：ReAct 每一步只看当下（局部贪心），Plan-and-Execute
  先有全局蓝图再动手。
- 什么时候值得：任务能被预先拆解（"调研 X、对比 Y、写成报告"），步骤间
  有明确依赖或可并行。
- 什么时候失效：目标本身在探索中演化（"看看这个 bug 是怎么回事"）——
  计划会连续过时，Re-plan 成本反而高于直接 ReAct。
- 工程要点：计划要落盘成结构化数据（不是一段散文），否则没法跟踪进度、
  没法做 Re-plan 的 diff。

## 3. Reflection：用"批判者"提升"执行者"

```text
任务 ──▶ Draft（初稿）
              │
              ▼
        Critique（同一模型或更强模型按 rubric 挑毛病）
              │
              ▼
        Revise（带着批评意见改稿）──▶ 满意？──否──▶ 再 Critique
              │                        │
              ▼                        是
            产出                 （设 max_iterations！）
```

- **为什么有效**：生成和评审是两种难度——模型"写对"难，"看出哪里不对"
  相对容易；批评意见作为上下文能显著改善下一版。
- **变体**：
  - Self-Refine：自己写自己批自己改。
  - Reflexion：把"失败执行的语言化总结"存进记忆，下一轮带上。
  - LLM-as-judge 打分（W3 Day6 实测过）就是 Reflection 的评估零件。
- **两个坑**（本次 RAGAS 实验都有体感）：
  1. judge 有偏好（长度/位置/自我偏好），critic 会把答案往"更长"批；
  2. 必须设 `max_iterations`，否则模型会无限打磨——和 ReAct 的 MAX_STEPS
     同一个保险丝逻辑。

## 4. Multi-Agent：分工、隔离、制衡

```text
              ┌────────────┐
              │ Orchestrator │（拆解/分发/汇总，本身可以是 Plan-and-Execute）
              └──────┬───────┘
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   Agent-检索    Agent-写作    Agent-审查     ← 各自独立上下文、各自工具集
        └────────────┼────────────┘
                      ▼
                  最终产出
```

- **真实收益只有两个半**：
  1. 上下文隔离（每个 Agent 只带自己需要的资料，注意力不被稀释）；
  2. 真并行（独立子任务同时跑）；
  2.5. 制衡（审查者与写作者利益分离，减少自嗨）。
- **三个代价**：通信 token 爆炸（消息在人之间传每跳都要完整表述）、
  错误级联（上游一个误判下游全错）、调试困难（十几轮对话谁也说不清
  哪步跑偏）。
- **Anthropic 的工程建议**（多智能体研究系统博文）：能一个 Agent 干的活
  不要上多 Agent；只在"任务可真并行 + 单上下文装不下"时使用。
- 本仓库的 stance：阶段一先用单 Agent + 好工具把事办成，Multi-Agent 留到
  阶段三项目里按需引入。

## 5. 怎么选：一个决策路径

```text
任务能一步说清吗？──是──▶ 直接 LLM 调用（别上 Agent）
        │否
        ▼
需要外部工具/知识吗？──否──▶ CoT + Reflection 即可
        │是
        ▼
路径能预先规划吗？──能──▶ Plan-and-Execute（执行层用 ReAct）
        │否                    │
        ▼                     └──质量要打磨？──是──▶ 套 Reflection
ReAct（设 MAX_STEPS）
        │
        ▼
子任务真独立 + 上下文装不下？──是──▶ 才考虑 Multi-Agent
```

记忆口诀：**先用最笨的，再换更聪明的；先单 Agent，再考虑多 Agent。**
复杂度本身就是成本，模式是拿来解决问题的，不是拿来炫技的。

## 6. 面试话术（60 秒版）

> Agent 的四大模式是 ReAct、Plan-and-Execute、Reflection 和 Multi-Agent。
> ReAct 是推理和行动交替的基础循环，所有模式的执行层都是它；Plan-and-Execute
> 把规划和执行解耦，用全局计划避免局部贪心跑偏；Reflection 用"批判-修订"
> 循环提升生成质量，本质是利用了"评审比生成容易"的不对称性，工程上必须
> 设迭代上限；Multi-Agent 用分工和上下文隔离换并行与制衡，但通信开销和
> 错误级联让它的适用面最窄。我的选型原则是从 ReAct 起步，逐步加模式——
> 我实际手写过 ReAct 循环（纯 prompt 协议版和 Function Calling 版都写过），
> 也实测过 tool_choice 在不同网关上的支持差异，所以清楚每层协议的真实边界。
