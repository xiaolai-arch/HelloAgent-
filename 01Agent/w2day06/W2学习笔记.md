## 0. 本周一句话

> **Prompt 不是“对模型说的话”，而是一份包含角色、任务、上下文、示例、输出契约和边界的完整规格说明。**

W2 做了三组对照实验，分别回答三个问题：

| 实验 | 问题 | 结论 |
|---|---|---|
| Day1 LangGPT | 结构化角色 Prompt 比普通提问好吗？ | 结构命中率显著提升，但 prompt tokens 约 30x；复杂模板要预留输出预算 |
| Day2 Zero/Few/CoT | 示例和逐步推理哪个更划算？ | 简单题 Zero-shot 够用；格式锁定用 Few-shot；多步推理用 CoT，但 token 成本最高 |
| Day3 System vs User | System Prompt 到底值不值？ | 结构、口径、安全行为显著改善；总 tokens 约 2.2x，价值在“可预测性”而不是“更聪明” |

## 1. 一页速览

```text
Prompt Engineering
├── 结构层：Role / Goals / Rules / Workflow / OutputFormat
├── 策略层：Zero-shot / Few-shot / Chain-of-Thought
├── 分层：System（稳定） vs User（变化）
├── 评估：正确性 / 结构 / 约束 / token / 延迟
└── 边界：Prompt 不是安全边界
        │
        ▼
Context Engineering（Day6 延伸）
├── 预算：token / attention / cost
├── 压缩：摘要 / 裁剪 / 引用 / 子 Agent
└── 记忆分层：working / session / long-term / external
```

三个最容易记住的结论：

1. **结构 > 形容词。** “专业、详细、结构化”不如直接给章节、字段和排序规则。
2. **示例锁格式，不教推理。** 只给“问题 → 答案”的 Few-shot，模型学到的是输出形状。
3. **Prompt 是上下文的一部分。** 当任务从单轮问答变成多轮 Agent，真正要管理的是整个 context window。

## 2. Day1：LangGPT 结构化 Prompt

### 2.1 实验设计

- 同一个问题、同一个模型、同一个温度（0.7）、同样的 `max_tokens=1200`。
- 普通组：问题直接作为一条 user 消息。
- 结构化组：System 放 LangGPT 模板，User 放同一个问题。
- 每组跑 2 次，观察结构稳定性和 token 成本。

测试问题：

> 什么是自注意力机制？请用通俗的语言解释，并给一个生活化类比帮助理解。

完整报告：[langgpt_compare_report.md](../w2day01/langgpt_compare_report.md)

### 2.2 结果

| 组别 | 轮次 | 结构命中 | 类比边界 | 自测 | Q/K/V | 中文字数 | prompt | completion | 思考 | finish |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 普通 Prompt | 1 | 0/5 | 否 | 否 | 是 | 712 | 27 | 897 | 22 | stop |
| 普通 Prompt | 2 | 1/5 | 否 | 否 | 是 | 694 | 27 | 854 | 22 | stop |
| 结构化 Prompt | 1 | 0/5 | 否 | 否 | 否 | 0 | 826 | 1200 | 1200 | length |
| 结构化 Prompt | 2 | 5/5 | 是 | 是 | 是 | 493 | 826 | 1102 | 596 | stop |

### 2.3 三个发现

**发现 1：结构是“输出契约”，不是装饰。**

结构化组第 2 次严格输出了五段式：一句话定义、生活化类比、工作机制、常见误区、自测。普通组虽然内容也不错，但结构每次不同，无法稳定对比，也无法直接接入下游流程。

**发现 2：结构化 Prompt 的 prompt tokens 约 30x。**

27 → 826 tokens，约 30.6 倍。其中 768 tokens 命中缓存（`cached_tokens=768`），说明稳定前缀确实可以降低成本；但第一次调用仍然要为完整模板付费。

**发现 3：`max_tokens` 太紧，会把输出预算耗在 reasoning 上。**

结构化组第 1 次 `completion=1200`、`reasoning_tokens=1200`、`finish_reason=length`，正文为空。原因是推理模型把 1200 tokens 全部用于内部思考，没有留下可见输出。

这不是“模板失败”，而是**预算分配失败**。修法：

- 提高 `max_tokens`（至少给正文留 800~1200 tokens）；
- 或换非推理模型做纯格式任务；
- 或在 Prompt 里限制“不要展开内部推理，直接按格式输出”；
- 或把复杂模板拆成“先列提纲，再展开”的两步调用。

### 2.4 可以复用的部分

- 五段式输出格式：定义 → 类比 → 机制 → 误区 → 自测。
- “类比元素 → 技术概念”对照表：让类比可检查，而不是文艺比喻。
- 强制写“类比失效边界”：防止读者过度类推。
- 自测题只出题、不给答案：把“理解”变成可检验的动作。

### 2.5 需要改进的部分

- 300~450 字对复杂概念偏紧，容易为了压缩而牺牲准确性。模板 v1.1 已改为“默认 300~450 字，复杂概念可放宽到 1.5 倍”。
- 每组只有 2 次，样本太小，不能当作普遍规律。
- 没有记录延迟；结构化 Prompt 的首 token 延迟和总延迟可能更高。

## 3. Day2：Zero-shot / Few-shot / Chain-of-Thought

### 3.1 实验设计

- 4 道集合应用题，含 1 道“只参加一门”的语义陷阱题。
- 同一个模型、`temperature=0.2`、`max_tokens=2000`。
- 三种策略各跑 4 题，共 12 次调用。
- 评分 100 分：答案正确 60，至少 2 个步骤标记 20，提到集合关系/公式 10，最后出现“答案：X”10。
- Few-shot 只给“问题 → 答案”，不展示推理过程，避免悄悄变成 Few-shot CoT。

完整报告：[prompt_strategies_report.md](../w2day02/prompt_strategies_report.md)

### 3.2 结果

| 策略 | 正确率 | 平均分 | 平均 prompt | 平均 completion | 平均 total | 中文字数 | 格式规范率 | 步骤展示率 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Zero-shot | 4/4 (100%) | 90.0 | 68 | 525 | 593 | 117 | 0% | 100% |
| Few-shot | 4/4 (100%) | 77.5 | 189 | 261 | 450 | 56 | 50% | 25% |
| Chain-of-Thought | 4/4 (100%) | 100.0 | 132 | 693 | 825 | 192 | 100% | 100% |

### 3.3 四个发现

**发现 1：正确率饱和，说明题目太简单。**

三种策略都是 4/4。继续比较“谁更准”没有意义，真正的差异在过程质量、格式稳定性和 token 成本。下次应该加入更难的多步题、干扰项和分布外题目。

**发现 2：CoT 最贵，但过程最可审计。**

CoT 平均 825 total tokens，是 Few-shot 的 1.83 倍、Zero-shot 的 1.39 倍。它换来了 100% 的格式规范率和步骤展示率，适合需要人工复核、教学或高风险决策的任务。

**发现 3：Few-shot 最便宜，但它学到的是“形状”。**

Few-shot 平均 450 total tokens，比 Zero-shot 还少 24%。因为示例把输出压得很短，模型直接模仿“答案：66”的形状，步骤展示率只有 25%。它适合“格式固定、答案简单”的任务，不适合“必须展示推理”的任务。

**发现 4：Zero-shot 不是“差”，是“默认”。**

Zero-shot 平均 593 tokens，正确率 4/4，步骤展示率 100%（因为模型自发写了过程）。在简单任务上，它是最便宜的起点；只有在失败模式明确时，才值得加示例或加 CoT。

### 3.4 策略选择表

| 任务特征 | 首选 | 原因 |
|---|---|---|
| 简单分类、抽取、改写 | Zero-shot | 最便宜，模型通常够用 |
| 输出字段/语气/格式必须稳定 | Few-shot | 示例比规则更擅长锁形状 |
| 多步计算、条件推理、易漏陷阱 | CoT | 显式步骤降低跳步和漏条件 |
| 高风险、需人工复核 | CoT + 结构化输出 | 过程可审计，答案可定位 |
| 推理模型 + 简单任务 | Zero-shot / 短 CoT | 内部已有思维链，外部 CoT 可能重复 |
| 长文档问答 | RAG + 引用 + 简短依据 | 先解决“资料是否在上下文里”，再谈推理 |

### 3.5 实验局限

- 只有 4 道题，每题只跑 1 次，样本很小；结论应理解为“这次实验中的趋势”。
- 题目都是集合/百分比应用题，不能直接推广到写作、代码、抽取。
- 自动判分只看最终数字和结构特征，不能判断推理是否真正严谨。
- Few-shot 示例只给答案；如果示例带推理，结果可能接近 Few-shot CoT。

## 4. Day3：System Prompt vs User Prompt

### 4.1 分工

| 维度 | System Prompt | User Prompt |
|---|---|---|
| 位置 | OpenAI 兼容接口的 `role: system`；Anthropic 的顶层 `system` 参数 | `messages` 里的 `user` 消息 |
| 生命周期 | 整个会话/整个应用稳定生效 | 每一轮单独变化 |
| 主要作用 | 定义“你是谁、为谁服务、守什么规矩、怎么输出” | 提供“这一轮要处理什么” |
| 内容 | 角色、目标、边界、语气、输出 schema、安全策略、工具规则 | 具体问题、代码、文档、数据、临时参数 |
| 变化频率 | 低（版本化、可复用） | 高（每轮都不同） |
| 调试入口 | 行为不对 → 改 System | 任务不对 → 改 User |
| 缓存友好 | 稳定前缀，利于 prompt caching | 变化部分，放在后面 |

一句话：

> **System 定“人设和规矩”，User 给“材料和任务”。**

### 4.2 实验设计

- 同一段有安全与质量问题的 FastAPI 代码。
- 两组唯一差异：是否加入“资深 Python 代码审查专家”System Prompt。
- 评分 100 分：结构 30 + 关键风险覆盖 30 + 级别使用 20 + 安全输出 10 + 测试建议 10。

完整报告：[demo_report.md](../w2day03/demo_report.md)
完整 System Prompt：[system_prompt_code_reviewer.md](../w2day03/system_prompt_code_reviewer.md)

### 4.3 结果

| 组别 | 得分 | 结构 | 关键风险覆盖 | 泄露完整假密钥 | 测试建议 | prompt | completion | 思考 | total |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 无 System | 30.0 | 0/5 | 3/3 | 是 | 否 | 269 | 1485 | 11 | 1754 |
| 有 System | 100.0 | 5/5 | 3/3 | 否 | 是 | 1772 | 2113 | 581 | 3885 |

### 4.4 四个发现

**发现 1：System Prompt 的主要价值是“可预测性”。**

无 System 组其实也识别出了 SQL 注入、硬编码密钥、密码哈希泄露，甚至额外发现了 `finally` 中 `conn` 未定义的边界问题。它有洞察，但没有固定章节、没有统一严重级别，输出无法直接进入 CI/评审流程。

有 System 组严格输出：结论 → 风险摘要 → 问题清单 → 建议测试 → 待确认；使用 `Blocker/Major/Minor` 分级；问题数量控制在 7 条；给出 5 条可执行测试。

**发现 2：安全行为可以被 System Prompt 改善，但不能被它保证。**

无 System 组在问题清单里原样复述了完整假密钥；有 System 组写成 `sk-live-...` 掩码。差别来自 System 里的“敏感值只指出位置、不复述完整值”。

但这只是**行为约束**，不是安全边界。真正的密钥保护、权限校验、注入防护必须在代码层实现。

**发现 3：成本是真实的。**

prompt 269 → 1772（约 6.6x），completion 1485 → 2113，total 1754 → 3885（约 2.2x）。换来的是结构稳定、口径统一、敏感值处理更安全。

**发现 4：System Prompt 不是越长越好。**

这套模板 1772 tokens，已经接近很多小任务的全部预算。如果只是“总结一段文字”，不值得用这么长的 System。模板长度应该跟任务风险和复用次数匹配。

### 4.5 System Prompt 的推荐结构

```text
1. 角色定义（Role）
   - 你是谁、经验、服务对象
   - 你擅长什么、不擅长什么

2. 目标（Goal）
   - 这类任务要交付什么结果
   - 什么叫“做完了”

3. 行为边界（Boundaries）
   - 不做什么
   - 缺信息怎么办
   - 不确定怎么表达
   - 安全/合规红线
   - 严重级别/判断标准

4. 输出规范（Output Specification）
   - 固定章节/字段/表格
   - 排序规则、长度、语言
   - 必须包含什么、禁止包含什么

5. 工作流程（Workflow）
   - 先看什么、再看什么
   - 如何从输入走到输出
   - 自检步骤

6. 初始化（Initialization）
   - 收到输入后第一句话说什么
   - 不要自我介绍、不要寒暄
```

不是每个 Prompt 都需要六块。任务简单时可以合并；但**角色、边界、输出**这三块最好不要省，因为它们是“专业感”和“可预测性”的主要来源。

### 4.6 Right Altitude（合适的高度）

Anthropic 用“right altitude”形容 System Prompt 的粒度：

- **太低**：把复杂业务逻辑写成 if-else 硬编码，Prompt 脆弱、难维护。
- **太高**：只给“你要专业、要准确”这种空话，模型没有可执行的信号。
- **合适**：具体到能指导行为，又保留模型根据上下文判断的空间。

一个检查方法：

> 如果一条规则换一个业务场景就失效，它可能太低；如果一条规则无法判断“什么算遵守”，它可能太高。

## 5. 知识点补齐（非仓库实验）

> Day4~Day5 没有可复核的实验数据，以下是把 W2 需要的概念补齐，便于串成体系。

### 5.1 Prompt 的解剖学

一个完整的 Prompt 通常包含 7 块：

| 块 | 回答的问题 | 放 System 还是 User |
|---|---|---|
| 角色 | 你是谁、为谁服务 | System |
| 任务 | 这一轮要做什么 | User |
| 上下文 | 有哪些材料、背景、约束 | User（大量材料） / System（稳定规则） |
| 示例 | 什么是“好输出” | System（固定示例） / User（本轮示例） |
| 输出契约 | 章节、字段、格式、长度 | System |
| 边界 | 不做什么、缺信息怎么办 | System |
| 工具 | 能用什么、怎么用 | System / 工具定义 |

### 5.2 指令优先级

- 逻辑上：System > User；本轮 User 不能覆盖 System 的硬约束。
- 但这不是安全保证：Prompt injection 可以把恶意指令藏在网页、文档、代码注释里。
- 正确做法：**把“指令”和“数据”分开**，数据用 `<document>`、`<code>` 等标签包起来；高风险操作加代码层校验和人工确认。

### 5.3 采样参数（与 W1 呼应）

| 参数 | 作用 | 常见误区 |
|---|---|---|
| `temperature` | 控制随机性 | 越低越确定，但不等于“更正确” |
| `top_p` | nucleus sampling | 通常只调 temperature 或 top_p 之一 |
| `max_tokens` | 输出上限 | 太小会截断；推理模型的 reasoning 也占这个预算 |
| `reasoning_tokens` | 内部思考消耗 | 不是所有模型都暴露；预算要单独留 |
| `finish_reason` | 停止原因 | `length` 往往意味着预算不够，不是模型不会 |

### 5.4 评估 Prompt 的最小方法

1. **固定变量**：同模型、同温度、同 `max_tokens`、同一组输入。
2. **只改一个东西**：有无 System、策略 A/B、模板版本 A/B。
3. **准备 5~10 个用例**：至少 1 个边界、1 个对抗、1 个“信息不足”。
4. **分开打分**：正确性、结构、约束遵守、成本。
5. **记录失败模式**：没理解任务、没遵守格式、编造事实、上下文不够。
6. **不要用一次输出下结论**：至少跑 2~3 次，观察方差。

### 5.5 安全边界

- Prompt 里不要放密钥、密码、token。
- System Prompt 不是保险箱；它仍然进入模型上下文，可能被套出来。
- 敏感值处理要写进 System（只指出位置、不复述完整值），但真正的脱敏要在代码层做。
- 对外部文档/网页/代码，默认按“不可信输入”处理。
- 高风险动作（转账、删除、发邮件、改权限）要有工具层权限和人工确认。

## 6. 三组实验放在一起看

| 实验 | 自变量 | 最大收益 | 最大代价 | 适用场景 |
|---|---|---|---|---|
| Day1 结构化 Prompt | 有无 LangGPT 模板 | 输出结构稳定、可对比 | prompt tokens 约 30x；推理预算可能被挤占 | 教学、内容生产、需要固定章节 |
| Day2 推理策略 | Zero/Few/CoT | CoT 过程可审计；Few-shot 锁格式；Zero 最便宜 | CoT token 成本最高；Few-shot 可能抑制推理 | 数学、抽取、分类、格式化工件 |
| Day3 System Prompt | 有无专业角色 System | 结构、口径、安全行为显著改善 | total tokens 约 2.2x；模板维护成本 | 生产级审查、客服、合规、工具调用 |

一个统一的判断公式：

```text
净收益 = 任务价值 × 质量提升 - token 成本 - 延迟成本 - 维护成本
```

如果任务价值低、调用量大，先优化成本和稳定性；如果任务风险高、人工复核贵，优先买结构和可审计性。

## 7. 八条可复用原则

1. **先写输出契约，再写形容词。** 章节、字段、排序、长度，比“专业、详细”有用。
2. **稳定前缀放 System，变化负载放 User。** 职责清晰，也利于缓存。
3. **示例锁格式，不教推理。** 要教推理，就给带步骤的示例，或者用 CoT。
4. **CoT 按需使用。** 多步、易错、需审计时用；推理模型上先算 ROI。
5. **预算要分开算。** prompt / completion / reasoning / 缓存命中，各自影响不同。
6. **用最小高信号上下文。** 能删的客套话、重复规则、无效示例都删掉。
7. **Prompt 不是安全边界。** 密钥、权限、注入防护必须在代码层。
8. **用数据说话。** 正确率、结构命中率、token、延迟，至少记录两个。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| Prompt | 发给模型的指令与上下文 |
| System Prompt | 稳定的角色、规则、输出规范 |
| User Prompt | 本轮任务与材料 |
| Zero-shot | 不给示例，直接任务 |
| Few-shot | 给少量示例，让模型模仿模式 |
| Chain-of-Thought (CoT) | 要求模型显式写出推理步骤 |
| Temperature | 采样随机性 |
| Top-p | nucleus sampling 的累积概率阈值 |
| Max tokens | 输出 token 上限 |
| Reasoning tokens | 推理模型内部思考消耗的 token |
| Context window | 模型一次能看到的 token 总量 |
| Prompt caching | 缓存稳定前缀，降低重复计费/延迟 |
| Context rot | 上下文越长，模型召回和推理越容易退化 |
| Right altitude | System Prompt 的粒度：够具体，又不写死 |
