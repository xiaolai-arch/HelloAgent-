# 混合检索与重排

## Dense vs Sparse

- **Dense（稠密/向量检索）**：语义匹配，能理解"退货≈退款"这类同义改写；弱项是精确词——错误码、产品型号、人名缩写容易被语义平滑掉。
- **Sparse（稀疏/BM25 检索）**：基于词频的经典算法（TF-IDF 的改进版，带词频饱和度和文档长度归一化），精确匹配强、可解释、零成本；弱项是完全不懂同义词，换个说法就找不到。

两者强项几乎互补，所以生产 RAG 常用 Hybrid（混合检索）：双路各召回一批，再融合排序。

## RRF：按排名融合

RRF（Reciprocal Rank Fusion）是融合两路结果最常用的公式：

```text
score(d) = Σ 1 / (k + rank_i(d))    # k 常取 60
```

每个文档的融合分 = 它在各路结果里的排名倒数之和。只用排名、不用原始分数，因为 BM25 分数和余弦相似度量纲完全不同没法直接相加，而排名是无量纲的——这就是 RRF 简单稳健的原因。

## Rerank：用 Cross-Encoder 精排

召回阶段用的 Bi-Encoder 把查询和文档分别编码成向量（快，但两段文本没有互相看过）；重排阶段的 Cross-Encoder 把 (query, chunk) 拼在一起送进模型逐对打分（慢，每对都要跑一次模型，但精度高）。所以标准做法是"漏斗"：宽召回（双路各取 20~50 条）→ 融合 → 重排取 top 5~10 → 进上下文。BGE-Reranker 是常用的开源重排模型；没有专用 rerank 服务时，也可以用 LLM 对候选逐条打分充当重排器，代价是延迟和 token 成本。

## Contextual Retrieval

Anthropic 提出的做法：切分后让模型为每个 chunk 生成 50~100 token 的文档级背景说明，拼在 chunk 前面再做索引。chunk 不再是"孤立碎片"，检索失败率在其 benchmark 上显著下降（Embedding +35%、加 BM25 +49%、再加 rerank +67%）。它解决的问题是：chunk 缺少"我来自哪份文档、讲什么背景"的上下文。

## lost in the middle

研究表明模型对放在上下文中间位置的信息利用最差，对开头和结尾最好。所以打包上下文时，最相关的资料应放在开头或结尾，不要埋在中间。
