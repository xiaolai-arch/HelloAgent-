# ReAct 循环：手写最小 Agent 实验报告（W4 Day1）

- 生成时间：2026-10-21 16:47:01
- 模型：`mimo-v2.6-flash`（temperature=0）
- 实现方式：纯 Prompt 协议 + 字符串解析（不用框架、不用 Function Calling）

## 一、ReAct 流程图解（白板版）

```text
        ┌────────────────────────────────────────────┐
        │              用户问题（Question）            │
        └──────────────────┬─────────────────────────┘
                           ▼
        ┌────────────────────────────────────────────┐
  ┌────▶│  Thought：我知道什么？还缺什么？下一步干什么？│
  │     └──────────────────┬─────────────────────────┘
  │                        ▼
  │     ┌────────────────────────────────────────────┐
  │     │  Action：选一个工具 + 给出输入               │
  │     └──────────────────┬─────────────────────────┘
  │                        ▼
  │     ┌────────────────────────────────────────────┐
  │     │  你的代码执行工具 → Observation（真实事实）   │
  │     └──────────────────┬─────────────────────────┘
  │                        │ 拼回上下文
  └────────────────────────┘ （信息够了 → Final Answer）
```

### 为什么比单纯 Reasoning 强

- 模型的参数知识是**静态且会幻觉**的；Action 把不确定的部分外包给真实工具，
  Observation 把事实塞回上下文，下一步推理从"凭记忆"变成"凭证据"。
- 推理决定"下一步做什么"（规划），行动获取"事实依据"（接地），
  两者交替 = 会用工具的 System 1 + System 2。
- 本实验里模型被明确要求"数值必须 calculate、事实必须 search"，
  把两类幻觉（算错数、编造制度）分别堵在工具后面。

## 二、协议设计（system prompt 即协议）

ReAct 没有任何 API 魔法，四个要素全部是提示词约定：

```text
Thought: 分析+决策        ← 模型生成
Action: 工具名            ← 模型生成（受限在工具列表内）
Action Input: 工具输入    ← 模型生成
Observation: 工具结果     ← 你的代码生成，模型只许读不许编
```

终止条件两种：模型输出 `Final Answer`（正常），或达到 MAX_STEPS=6（防打转，所有 Agent 框架的标配保险丝）。

## 四、观察与结论

1. **协议可用但脆弱**：2/2 题的工具覆盖符合预期，出现 2 次格式违规。纯文本协议没有 Schema 约束，
   模型偶尔会把 Action 和 Final Answer 混在一行——这正是 Day2 Function Calling 要解决的问题：**协议进 API 层，解析交给协议**。
2. **Observation 是防幻觉的锚**：检索工具把制度原文塞进上下文后，
   回答里出现了"财务经理加签"这类可追溯细节——对照 W2 的实验：
   有证据的生成比裸生成可靠。
3. **循环上限是安全带**：MAX_STEPS 防止模型在同一个工具上打转烧钱；
   生产 Agent 还需要：工具超时、结果截断（本例 Observation 截到 400 字）、
   重试与降级。
4. **上下文滚动成本**：每一步把全部历史重发一遍，步数越多 prompt
   tokens 越长——Agent 的费用曲线是二次的，这直接通向 Context
   Engineering 的预算/压缩议题（W2 延伸、阶段四 W16）。
