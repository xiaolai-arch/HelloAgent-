# Context Engineering：从 Prompt 到上下文生命周期

> 面向面试与工程实践的速查 + 话术手册。
> 对应 W2 Day6 延伸；阶段四 W16 再展开。
> 核心不是背定义，而是能讲清「预算、压缩、记忆分层」三个杠杆，并用自己做过的实验举例子。

---

## 0. 先背这 5 句

1. **Prompt Engineering 解决“怎么说”，Context Engineering 解决“让什么进入窗口、以什么形式、何时进入、如何留下”。**
2. **上下文有三种预算：token 预算、注意力预算、成本/延迟预算。** 三者同时存在，不能只数 token。
3. **长上下文 ≠ 好上下文。** Context rot 是普遍现象，更多 token 往往带来更多干扰。
4. **压缩的首选不是“删掉”，而是“可恢复地引用”；记忆的首选不是“全存”，而是“分层 + 按需召回”。**
5. **面试时不要否定 Prompt Engineering。** 把它定位成 Context Engineering 的指令层，既准确，也显得你有工程演进视角。

## 1. 行业为什么从 Prompt 转向 Context

### 1.1 从单轮问答到多轮 Agent

单轮任务的上下文是“一次写好的 Prompt”；Agent 的上下文是“一个不断增长的轨迹”：

```text
用户输入 → 模型决策 → 工具调用 → 工具结果 → 模型再决策 → ……
```

每一轮都会把新的动作和观察追加进上下文。任务越长，上下文越像一条越来越长的日志，而不是一段精心写好的话。

Manus 的工程博客给了一个很直观的比例：在其 Agent 场景中，平均输入/输出 token 比约为 **100:1**。输出通常是一个短的结构化动作，输入却是整条轨迹。这意味着 prefill（预填充）而不是 decoding（解码）主导了成本和延迟。

结论：

> **Agent 的核心工程问题，不是“怎么把一句话写好”，而是“怎么管理一条不断增长的上下文轨迹”。**

### 1.2 Context rot：窗口大，不等于看得清

Chroma 在 2025 年的 *Context Rot* 报告里评估了 18 个模型，发现即使任务很简单，模型表现也会随着输入长度增加而下降；干扰项（distractors）、低相似度的 needle-question pair、结构化的 haystack 都会让问题更严重。

另一个实验更直观：LongMemEval 里，**只给相关片段（约 300 tokens）** 的表现，普遍好于 **给完整对话历史（约 113k tokens）**。模型不是“看得多就懂得多”，它还要先做检索，再做推理；无关上下文会稀释注意力。

Anthropic 的解释是：Transformer 的注意力是 n² 的成对关系，上下文越长，注意力越容易被“摊薄”；模型在训练中见到的长序列也更少。于是所谓“上下文窗口”是一个性能渐变，而不是一个硬 cliff。

这就是 **attention budget（注意力预算）**：窗口能装 200k tokens，不代表 200k tokens 都能被同等有效地利用。

### 1.3 成本与延迟：token 不是免费的

- 输入 token 要计费，输出 token 更贵。
- 长上下文增加 prefill 时间，首 token 延迟（TTFT）变高。
- Agent 的输入/输出比很高，prefill 是主要成本。
- KV-cache 能显著降低成本，但前提是前缀稳定、上下文 append-only。

Manus 举过一个价格例子：在当时的 Claude Sonnet 上，缓存输入约 **$0.30/MTok**，未缓存输入约 **$3/MTok**，差 **10 倍**。价格会变，但结论不变：**缓存命中率是生产级 Agent 的一等指标。**

### 1.4 上下文来源爆炸

今天的上下文不只来自 Prompt：

- System Prompt / 开发者指令
- 工具定义（function calling / MCP）
- Few-shot 示例
- RAG 检索结果
- 文件系统、代码库、网页
- 会话历史、工具输出
- 长期记忆、用户画像
- 子 Agent 的摘要

Prompt Engineering 只覆盖其中一小块。Context Engineering 要处理的是**整个 token 状态**：哪些进来、哪些留在外面、哪些压缩、哪些持久化。

### 1.5 模型变强：少写死，多给上下文

Anthropic 在 *Effective context engineering for AI agents* 里提到一个趋势：模型越强，越不需要把复杂业务逻辑写成 if-else 硬编码；更好的做法是给模型清晰的工具、目标和判断标准，让它自己决定怎么用上下文。

这不意味着 Prompt 不重要，而是：

> **Prompt 从“操作手册”变成了“行为契约 + 上下文接口”。**

### 1.6 一张表看清转变

| 维度 | Prompt Engineering | Context Engineering |
|---|---|---|
| 优化对象 | 一段文字 | 每次推理的 token 状态 |
| 时间尺度 | 单轮/单次 | 多轮/长时任务 |
| 主要问题 | 说清楚任务 | 选什么、放多少、何时放、如何留 |
| 成功指标 | 输出质量 | 任务成功率 + 成本/延迟 + 可审计 |
| 典型技术 | 角色、示例、CoT、输出格式 | 预算、检索、压缩、隔离、记忆 |
| 失败模式 | 指令模糊、格式不稳 | 上下文污染、膨胀、缺失、冲突 |
| 与另一个的关系 | 子集（指令层） | 超集（包含指令层） |

## 2. 定义与边界

### 2.1 三个可引用的定义

**Anthropic（2025-09）**：

> Context engineering 是“在 LLM 推理过程中，策划和维护最优 token 集合的策略”，包括 Prompt 之外所有可能进入上下文的信息。

**Karpathy（2025-06）**：

> “the delicate art and science of filling the context window with just the right information for the next step.”
> （把“刚好够用”的信息填进上下文窗口的技艺。）

**LangChain（2025-07）**：

> 用 **write / select / compress / isolate** 四类操作管理上下文。

### 2.2 我自己的定义（面试可用）

> **Context Engineering 是在每一次推理前，为模型构造一个高信号、低噪声、可追溯、可持续的 token 状态；并为下一次推理准备好写入、压缩、隔离和遗忘的机制。**

拆开看是四个词：

- **高信号**：留下的信息能影响决策。
- **低噪声**：重复、过期、无关的内容不进来。
- **可追溯**：关键结论知道来自哪份资料、哪次工具调用。
- **可持续**：多轮之后仍然能压缩、恢复、更新，而不是越跑越乱。

### 2.3 四个“不是”

- **不是“把 Prompt 写得更长”。** 长不等于好，可能只是噪声更多。
- **不是“RAG 的同义词”。** RAG 只是“选择外部知识”的一种手段。
- **不是“记忆”的同义词。** 记忆只是“跨会话持久化”的一层。
- **不是“评估/安全的替代品”。** 上下文工程做得再好，也不能替代权限、密钥管理、注入防护和评测。

### 2.4 一张图

```text
                 ┌──────────────────────────────────────────────┐
                 │                Context Window                │
                 │  system | tools | examples | retrieved docs  │
                 │  history | scratchpad | user | reserved out  │
                 └──────────────────────────────────────────────┘
                        ▲             ▲              ▲
                        │             │              │
                     select        compress       isolate
                        │             │              │
                 ┌──────┴─────────────┴──────────────┴──────┐
                 │   memory / files / vector DB / web / tools │
                 └───────────────────────────────────────────┘
                        ▲
                        │ write / consolidate / forget
```

## 3. 预算（Budget）：上下文的第一性约束

### 3.1 三种预算

| 预算 | 约束 | 超了会怎样 | 怎么度量 |
|---|---|---|---|
| Token budget | 窗口硬上限 | 请求失败/截断 | tokenizer 计数 |
| Attention budget | 有效注意力 | 召回下降、推理变差 | 任务指标随长度变化 |
| Cost/latency budget | 钱和时间 | 成本超支、P95 延迟高 | 账单、TTFT、总延迟 |

**Token budget 是硬约束，attention budget 是软约束，cost/latency 是业务约束。** 三者要一起算。

### 3.2 窗口解剖（以 200k 为例）

> 下面是经验区间，不是定律；不同任务差异很大。

| 部分 | 经验占比 | 示例 tokens | 说明 |
|---|---:|---:|---|
| System / policy | 2%~5% | 4k~10k | 角色、边界、输出契约、安全规则 |
| Tool definitions | 3%~5% | 6k~10k | 工具 schema、MCP 描述 |
| Few-shot examples | 2%~5% | 4k~10k | 少而典型，不要堆 edge case |
| Retrieved knowledge | 25%~40% | 50k~80k | RAG/文件/网页，重排后保留 |
| History / tool results | 20%~30% | 40k~60k | 多轮轨迹，最容易膨胀 |
| Scratchpad / notes | 2%~5% | 4k~10k | todo、计划、中间结果 |
| User input | 1%~5% | 2k~10k | 本轮任务与材料 |
| Reserved output | 20%~30% | 40k~60k | 可见输出 + reasoning |
| Safety margin | 5%~10% | 10k~20k | 防止估算误差/突发长输入 |

### 3.3 预算公式

```text
available_for_input = window_size - reserved_output - safety_margin
```

一个 200k 窗口的例子：

```text
window              200k
- reserved_output    40k   # 可见输出 + reasoning
- safety_margin      20k   # 10%
= available_input   140k

system/policy         4k
tools                 8k
examples              4k
retrieved docs       50k
history/tool results 40k
scratchpad            4k
user input           10k
buffer               20k
=                   140k
```

### 3.4 注意力预算：怎么让关键信息被看见

研究给出的实践建议：

- **关键指令放开头或结尾。** “Lost in the middle” 发现模型对中间位置的信息召回更差。
- **减少干扰项。** 不是“多给一点总没坏处”，干扰项会实打实降低表现。
- **重排后再打包。** 先召回 50~150 条，再 rerank 到 5~20 条。
- **去重。** 重复内容既浪费 token，也会放大某一类信息。
- **用显式分隔。** `<instructions>`、`<context>`、`<document>`、`<question>`，降低“资料里的指令被当成系统指令”的概率。
- **控制示例数量。** 2~5 个典型示例通常比 20 个 edge case 更有效。

### 3.5 KV-cache：预算的“价格维度”

KV-cache 的命中率直接影响成本和延迟。做法：

1. **保持前缀稳定。** 不要把时间戳、随机 ID、每轮变化的内容放在 System 开头。
2. **上下文 append-only。** 不要修改之前的动作/观察；序列化要确定性（JSON key 顺序稳定）。
3. **显式缓存断点。** 有些平台需要手动标记；至少覆盖 System Prompt 结尾。
4. **工具定义稳定。** 不要在循环中动态增删工具；Manus 的做法是“mask, don't remove”（用解码约束屏蔽，而不是删定义）。
5. **把缓存命中率纳入监控。** 它和任务成功率一样重要。

> 价格例子只用于说明量级：Manus 提到缓存输入与未缓存输入可差 10 倍。实际价格以当前供应商为准。

### 3.6 预算检查清单

- [ ] 每一类上下文都有 token 计数，而不是只算总 prompt。
- [ ] 给输出和 reasoning 预留了足够预算。
- [ ] 检索 top-k 和 rerank 后的 chunk 数有上限。
- [ ] 关键指令在开头/结尾，不在长上下文中段。
- [ ] 历史消息有裁剪/摘要策略，不是无限追加。
- [ ] 监控 cache hit rate、TTFT、P95 延迟、每任务成本。
- [ ] 有“超预算”降级策略（减少检索、摘要历史、切换小模型）。

## 4. 压缩（Compression）：把上下文变短，但不把信息弄丢

### 4.1 两种压缩

| 类型 | 做法 | 优点 | 风险 |
|---|---|---|---|
| 有损压缩 | 摘要、抽象、改写 | 省得多 | 丢细节、摘要漂移 |
| 可恢复压缩 | 保留指针（文件路径、URL、ID、工具调用 ID），按需再取 | 不丢信息 | 需要可访问的存储/工具 |

**优先可恢复压缩。** 只有确认“这段信息以后不会再需要”，才做有损压缩。

### 4.2 八种手法

| 手法 | 做法 | 省什么 | 风险 | 适用 |
|---|---|---|---|---|
| 摘要 / compaction | 把长轨迹压成结构化摘要 | 大量历史 tokens | 丢细节、摘要漂移 | 长对话、长任务 |
| 裁剪 / trimming | 删除旧消息、低分 chunk | 直接减少 tokens | 删掉后面才用到的信息 | 明确不再需要的旧内容 |
| 工具结果清理 | 保留调用和结论，删原始输出 | 工具输出往往最大 | 需要重放时拿不到原文 | 搜索、日志、文件读取 |
| 引用替代全文 | 只留路径/URL/ID | 极大 | 需要可靠的读取工具 | 文件、网页、数据库 |
| 结构化笔记 / recitation | todo.md、NOTES.md、计划表 | 用少量 token 保留目标 | 笔记本身会膨胀 | 多步任务、长时 Agent |
| 子 Agent 隔离 | 子 Agent 探索，主 Agent 只收摘要 | 隔离大量中间上下文 | 摘要可能漏关键信息 | 研究、检索、代码探索 |
| 按需检索 / progressive disclosure | 先给索引/路径，需要时再读 | 避免一次性灌入 | 多一次工具往返 | 大代码库、文档库 |
| 去重 / 格式压缩 | 去重复、表格化、精简 schema | 10%~30% 常见 | 过度压缩伤语义 | 所有场景 |

### 4.3 什么该留，什么该丢

**必须留：**

- 目标和约束（要做什么、不能做什么）
- 已做的关键决策（为什么选 A 不选 B）
- 未解决的问题 / 已知 bug
- 用户偏好和长期约束
- 关键事实的来源（provenance）
- 失败证据（错误信息、堆栈、失败动作）
- 下一步计划

**可以丢：**

- 原始工具输出（保留结论/引用即可）
- 重复的文档片段
- 寒暄、客套、无关对话
- 过期版本
- 低相关性的检索结果
- 已经完成的中间步骤的冗长细节

### 4.4 三个工业案例

**Claude Code 的 compaction：**

- 在上下文接近上限时（常见说法是 ~95%），把消息历史交给模型总结。
- 保留架构决策、未解决的 bug、实现细节；丢弃冗余工具输出。
- 继续时带上压缩摘要 + 最近访问的少量文件。
- 关键经验：**先最大化 recall，再优化 precision**。先保证不丢关键信息，再删多余内容。

**Manus 的文件系统即上下文：**

- 不把所有观察都塞进窗口；大对象放文件系统，上下文里留路径。
- 压缩必须“可恢复”：网页内容可以丢，但 URL 要保留；文档内容可以丢，但路径要保留。
- 用 `todo.md` 不断“复述”目标，把全局计划推到注意力最近的位置。
- **保留错误**：失败的动作和堆栈不要清理，模型需要证据来调整行为。
- **不要被 few-shot 进沟里**：上下文里太多相似的动作-观察对，会让模型机械模仿；需要引入少量结构化变化。

**子 Agent 隔离：**

- 子 Agent 可以有很长的探索上下文，但只向主 Agent 返回 1k~2k tokens 的蒸馏摘要。
- 主 Agent 保持高层计划，子 Agent 负责深度搜索。
- 代价是 token 总量可能更高（多 Agent 可能比单 Agent 贵很多），以及协调复杂度。

### 4.5 压缩的风险

- **过度压缩**：删掉了“当时看起来不重要、后面才关键”的信息。
- **摘要漂移**：每一轮摘要都在改写上一轮摘要，错误会累积。
- **来源丢失**：压缩后无法追溯结论来自哪份文档。
- **安全泄露**：摘要可能把敏感信息带到更宽的上下文里。
- **评估缺失**：只看 token 降了多少，不看任务成功率。

### 4.6 压缩的评估

| 指标 | 说明 |
|---|---|
| Token reduction ratio | 压缩后 / 压缩前 |
| Task success | 压缩后任务是否仍然完成 |
| Fact retention | 关键事实是否保留 |
| Reconstruction cost | 需要回读原文时，成本/延迟多少 |
| Faithfulness | 摘要是否忠实于原文 |
| Drift | 多轮压缩后是否偏离原始目标 |

> 压缩不是“删字比赛”，而是“在预算内保留决策所需信息”的工程问题。

## 5. 记忆分层（Memory Layering）：让该记住的记住，该忘的忘

### 5.1 OS 类比

Karpathy 把 LLM 比作新的操作系统：模型是 CPU，上下文窗口是 RAM，外部存储是磁盘。

- **上下文窗口 = 工作内存**：快，但小，断电就没。
- **文件/向量库/知识图谱 = 磁盘**：大，但需要读取。
- **记忆管理 = 操作系统的内存管理**：决定什么进 RAM、什么换出、什么持久化。

这个类比很好用，但要注意边界：OS 的内存管理是确定性的，LLM 的“记忆”是概率性的；检索可能错，摘要可能漂移。

### 5.2 七层记忆（从工作内存到模型参数）

| 层 | 存什么 | 生命周期 | 典型实现 | 读取方式 |
|---|---|---|---|---|
| **L0 工作上下文** | 当前指令、任务、最近几轮 | 单次推理 | Prompt / messages | 每轮必带 |
| **L1 会话状态** | 计划、todo、中间结果 | 单次会话 | state object、scratchpad、NOTES.md | 每轮/按需 |
| **L2 长期语义记忆** | 用户偏好、事实、实体关系 | 周/月 | 记忆库、知识图谱 | 检索 |
| **L3 长期情景记忆** | 过去的交互、决策、失败 | 月/年 | 事件日志、向量库 | 检索 |
| **L4 程序性记忆** | 规则、流程、技能 | 长期 | System Prompt、CLAUDE.md、skills | 常驻/按需 |
| **L5 外部知识** | 文档、网页、数据库 | 可变 | RAG、文件搜索、SQL | 按需 |
| **L6 模型参数** | 训练得到的通用知识 | 训练周期 | 预训练/微调 | 隐式 |

实际系统不需要全部实现。大多数 Agent 从 L0 + L1 + L5 开始，再逐步加 L2/L3。

### 5.3 三种记忆类型

| 类型 | 内容 | 例子 |
|---|---|---|
| Semantic（语义） | 事实、偏好、实体关系 | “用户偏好中文回答”“项目使用 FastAPI” |
| Episodic（情景） | 过去发生的事 | “上次部署失败是因为迁移脚本” |
| Procedural（程序） | 怎么做、规则、流程 | “代码审查按 Blocker/Major/Minor 分级” |

LangGraph 的长期记忆文档也采用类似分类：semantic / episodic / procedural。

### 5.4 记忆生命周期

```text
Write → Consolidate → Retrieve → Update → Forget → Audit
```

每个环节的关键问题：

**Write（写什么）**

- 只存“未来会改变行为”的信息：明确偏好、稳定事实、关键决策、可复用流程。
- 不存原始日志、重复对话、一次性细节。
- 写入要有来源、时间、置信度。

**Consolidate（巩固/合并）**

- 把多次情景记忆合并成语义记忆。
- 去重、解决冲突、补时间戳。
- 例：用户三次说“喜欢简洁回答” → 语义记忆“偏好简洁”。

**Retrieve（怎么取）**

- 相关性 + 新近性 + 重要性，三者加权。
- 混合检索（向量 + 关键词 + 元数据）。
- 权限过滤（ACL）先于相关性排序。
- 不要把所有记忆都塞进上下文。

**Update（怎么更新）**

- 新信息覆盖旧信息时，保留 `supersedes` 关系。
- 冲突时不要静默选一个；记录冲突，必要时问用户。
- 版本化，避免“记忆漂移”。

**Forget（怎么忘）**

- TTL：临时偏好、活动信息。
- 用户请求删除：必须可执行、可验证。
- 隐私/合规：敏感信息不长期保留。
- 低价值/长期不用：衰减或归档。

**Audit（怎么审计）**

- 每条记忆有来源、时间、置信度。
- 能回答“为什么模型会记得这个？”
- 能删除、能导出、能纠正。

### 5.5 架构案例

| 系统 | 记忆思路 | 值得借鉴 |
|---|---|---|
| **MemGPT / Letta** | 主上下文 + 外部上下文；模型通过工具自己编辑记忆 | 把记忆操作变成显式工具；OS 式分层 |
| **LangGraph** | thread-scoped 短期记忆 + cross-thread 长期记忆；semantic/episodic/procedural | 短期/长期分开；按 thread 隔离 |
| **Zep / Graphiti** | 时序知识图谱；记录事实的时间有效性 | 处理“旧事实/新事实”的冲突 |
| **Claude memory tool** | 文件式记忆目录；显式读写 | 简单、可控、可审计 |
| **CLAUDE.md / rules** | 程序性记忆，常驻上下文 | 稳定规则与任务数据分离 |
| **ChatGPT memory** | 自动生成用户记忆，跨会话选择 | 自动化的代价：选择错误会“串味” |

### 5.6 设计记忆时的 8 个问题

1. 哪些信息必须跨会话保留？哪些只是本轮/本会话？
2. 记忆的写入是显式（用户说“记住”）还是隐式（模型推断）？
3. 记忆的权威性如何排序？用户当前指令 > 旧记忆？
4. 冲突怎么处理？覆盖、并列、还是问用户？
5. 保留多久？TTL 是多少？
6. 谁可以访问？是否需要按用户/租户/项目隔离？
7. 怎么删除？删除后检索索引/缓存/摘要是否也删除？
8. 怎么评估？记忆命中率、错误记忆率、任务提升、隐私事件。

### 5.7 记忆反模式

- **全存**：把聊天记录全塞进向量库，检索噪声大、隐私风险高。
- **全取**：每次把所有记忆都放进上下文，等于没分层。
- **无 TTL**：过期偏好/旧事实一直影响行为。
- **无来源**：不知道记忆从哪来，无法纠错。
- **无冲突处理**：新旧事实并存，模型随机选一个。
- **记忆投毒**：恶意内容被写入长期记忆，持续影响后续会话。
- **记忆与 RAG 混为一谈**：RAG 是外部知识，记忆是用户/Agent 经验；写入路径和权限不同。
- **只评估最终答案**：不评估记忆命中/错误记忆，出了问题定位不到。

## 6. 统一框架：5R + 2×2 + 决策树

### 6.1 5R

| 步骤 | 问题 | 对应操作 |
|---|---|---|
| **Record** | 什么值得留下？ | 写记忆、记笔记、存文件 |
| **Retrieve** | 这次需要什么？ | RAG、搜索、读文件、查记忆 |
| **Rank** | 什么最可信/最相关？ | 相关性、时效、来源、权限 |
| **Reduce** | 怎么在预算内放下？ | 摘要、裁剪、引用、去重 |
| **Review** | 效果如何？该更新/遗忘什么？ | 评估、纠错、TTL、consolidation |

### 6.2 2×2

|  | 写入/持久化 | 读取/进窗口 |
|---|---|---|
| **In-context** | 提示词、笔记、临时状态 | 当前任务、最近对话 |
| **Out-of-context** | 文件、向量库、知识图谱、记忆库 | 检索、工具调用、子 Agent |

横切关注点：**预算、压缩、隔离、安全、评估**。

### 6.3 一个 Agent 的上下文流水线

```text
用户输入
  → 意图识别 / 任务分类
  → 加载稳定策略（System / policy）
  → 加载会话状态（todo、计划、中间结果）
  → 选择外部知识（RAG / 文件 / 工具 / 记忆）
  → 排序、过滤、压缩
  → 按预算组装 Prompt
  → 调用模型
  → 执行工具
  → 写回结果/笔记/记忆
  → 评估是否继续
  → 下一轮
```

### 6.4 信息放哪：决策树

```text
这条信息需要每轮都遵守吗？
├─ 是 → System / policy
└─ 否
   ├─ 只属于本轮任务？ → User
   ├─ 跨轮但只跨本次会话？ → State / scratchpad
   ├─ 跨会话且关于用户/项目？ → Long-term memory
   ├─ 大量外部知识？ → RAG / file search
   └─ 需要精确计算/实时数据？ → Tool / code / API
```

这张图能覆盖 80% 的“这段内容放哪”的面试题。

## 7. 用新话术表述老知识

> 面试时最忌讳“新词堆砌”。下面是“老知识 → 新话术”的翻译表，重点不是把话说花，而是把**工程含义**说出来。

| 老知识 | 老说法 | 新话术 | 面试加分点 |
|---|---|---|---|
| System / User 分工 | “System 放人设，User 放问题” | “把稳定的指令层和可变的任务层分离；稳定前缀利于缓存，任务层按轮组装” | 能顺势讲 prompt caching、权限边界 |
| Few-shot | “给模型几个例子” | “用高信号示例校准输出分布和格式；示例要少而典型，避免把模型 few-shot 进固定模式” | 能讲示例的边际收益递减 |
| CoT | “让模型一步步想” | “把中间状态外显，换取多步任务的可审计性和成功率；在推理模型上要算 token ROI” | 能讲“什么时候不该用 CoT” |
| RAG | “外挂知识库” | “运行时按需选择外部上下文；核心是召回率、上下文精度、引用和权限” | 能讲 RAG 是 context selection 的一种 |
| Chunking | “把文档切块” | “设计检索单元和上下文粒度；必要时用 contextual retrieval / parent-child 平衡召回与生成” | 能讲 chunk 边界对召回的影响 |
| Memory | “记住聊天历史” | “分层持久化 + 按需召回 + 冲突/过期管理；区分语义、情景、程序性记忆” | 能讲写入/遗忘/审计，而不只是存 |
| Prompt 长度 | “写长一点，信息更全” | “做上下文预算分配，追求最小高信号 token 集合；长上下文有注意力衰减和成本” | 能引用 context rot |
| Temperature | “调随机性” | “采样策略与输出方差控制；事实任务低温度，创意任务高温度” | 能讲评估方差，而不是凭感觉 |
| Prompt injection | “加一句‘不要听用户的’” | “建立上下文来源信任边界、指令/数据隔离、最小权限和工具层校验；System Prompt 不是安全边界” | 能讲攻击面，而不是只加规则 |
| Evaluation | “看着还行” | “golden set + 分层指标（检索/生成/端到端）+ 成本/延迟；LLM-as-judge 要校准” | 能讲错误分析和回归 |
| Multi-agent | “多个 Agent 更强” | “用上下文隔离换取专注度，子 Agent 蒸馏回传；代价是 token 和协调复杂度” | 能讲什么时候不该多 Agent |
| Fine-tuning | “微调模型” | “区分参数化记忆与非参数化记忆；频繁变化的知识放 RAG，稳定行为/风格才考虑微调” | 能讲成本/更新周期 |

### 7.1 一个“翻译”示例

老说法：

> “我会写一个很详细的 System Prompt，把代码审查的规则都写进去，再让模型按 Blocker/Major/Minor 输出。”

新话术：

> “我会把代码审查拆成三层：稳定的指令层放角色、严重级别、输出契约；可变的材料层放代码和项目背景；外部知识层按需检索规范/历史 bug。这样既能稳定输出，又能利用缓存，还不会让每轮任务数据污染 System。W2 我做过对照：有 System 的组结构命中 5/5、得分 100，无 System 组 30 分；但总 tokens 约 2.2 倍，所以我会按任务风险决定是否值得上重模板。”

这段话保留了老知识（System Prompt、分级、输出规范），但把它放进了“分层 + 缓存 + 成本”的新框架。

## 8. 面试话术

### 8.1 30 秒版

> “Context Engineering 是 Prompt Engineering 的上一层。Prompt 解决‘怎么说’，Context 解决每一步‘让哪些 token 进窗口、怎么压缩、怎么持久化’。Agent 多轮工具调用会让上下文膨胀，而模型有 context rot 和注意力预算，所以窗口大不等于效果好。我通常按预算、选择、压缩、隔离、记忆五步做，并用任务成功率、faithfulness、token 成本和缓存命中率评估。”

### 8.2 60 秒版

> “我会把上下文分成三类预算：token、注意力、成本/延迟。Token 是硬上限，注意力是软约束——Chroma 的 context rot 实验显示，输入越长，模型召回越容易退化；成本/延迟则决定这个方案能不能上线。
>
> 具体操作是四件事：第一，选择，只放高信号内容，RAG 先召回再重排；第二，压缩，优先可恢复压缩，比如保留文件路径/URL，而不是直接删；第三，隔离，用子 Agent 或命名空间把长探索隔开，只回传摘要；第四，持久化，把跨会话的信息放进分层记忆，区分语义、情景、程序性记忆。
>
> 我不会一上来就上 GraphRAG 或多 Agent，先把预算、解析、切分、评估做好，通常收益更大。”

### 8.3 2 分钟版（框架 + 例子）

> “我理解 Context Engineering 的核心是‘在有限注意力下做信息选择’。可以用 5R 记：Record、Retrieve、Rank、Reduce、Review。
>
> 以客服 Agent 为例：System 放政策、语气、升级规则；User 放本轮问题；RAG 检索产品文档和工单；客户账户信息通过 API 查，不放进长期记忆；历史对话超过预算就摘要，工具原始输出只留结论；跨会话只记用户偏好和未解决问题；最后用 golden set 评估答案正确率、引用准确率、该升级时是否升级、每会话成本。
>
> 我不会把所有东西都塞进 200k 窗口。Chroma 的实验显示，给模型完整 113k 对话历史，反而不如只给约 300 tokens 的相关片段。所以‘选对’比‘给多’重要。”

### 8.4 STAR 案例（用 W2 实验）

**Situation：**

> “W2 我做 Prompt 对照实验，想验证‘结构化模板是不是一定更好’。”

**Task：**

> “在同一个模型、同一温度、同一 max_tokens 下，比较普通提问、LangGPT 结构化模板、Zero/Few/CoT、以及有无 System Prompt。”

**Action：**

> “我固定变量，只改一个因素；给输出做结构命中、正确性、风险覆盖、敏感值处理打分；同时记录 prompt/completion/reasoning tokens。”

**Result：**

> “结构化组结构命中 5/5，普通组 0~1/5，但 prompt tokens 从 27 涨到 826，约 30 倍；CoT 得分 100，但平均 825 tokens，是 Few-shot 450 的 1.83 倍；System Prompt 组 100 分 vs 无 System 30 分，但总 tokens 约 2.2 倍。”

**Lesson：**

> “所以我的结论不是‘模板越重越好’，而是‘按任务价值和风险买结构’。低风险、高频任务用轻模板；高风险、需审计的任务才值得上重 System。这其实就是在做上下文预算。”

### 8.5 十问十答

#### Q1：什么是 Context Engineering？

**一句话：** 在每次推理前，为模型构造高信号、低噪声、可追溯的 token 状态，并管理它的写入、压缩、隔离和遗忘。

**展开：** 它比 Prompt Engineering 多管了工具定义、RAG、历史、记忆、文件、子 Agent；核心约束是 token、注意力和成本。

**别踩坑：** 不要只说“就是管理上下文窗口”，要说出“选择/压缩/隔离/持久化”的具体动作。

#### Q2：Prompt Engineering 过时了吗？

**一句话：** 没有，它变成了 Context Engineering 的指令层。

**展开：** 单轮任务仍然需要清晰指令、结构化输出、示例；Agent 场景多了上下文生命周期问题。两者是子集关系，不是替代关系。

**别踩坑：** 不要说“过时了，现在都讲 context engineering”，这会显得你在追词。

#### Q3：如何为一个 Agent 设计上下文？

**一句话：** 先画任务循环，再列上下文来源，然后做预算、选择、压缩、隔离、持久化、评估。

**展开：**

1. 任务循环：几步、哪些工具、哪些决策点。
2. 来源清单：System、工具、RAG、历史、记忆、文件。
3. 预算：窗口、输出预留、安全 margin。
4. 选择/排序：混合检索、rerank、ACL。
5. 压缩/隔离：摘要、引用、子 Agent。
6. 持久化：什么跨会话、什么 TTL。
7. 评估：任务成功率、faithfulness、成本/延迟。

**别踩坑：** 不要一上来选框架/向量库，先画信息流。

#### Q4：200k 窗口怎么分配？

**一句话：** 没有 universal ratio，但可以先按“输出 20~30%、检索 25~40%、历史 20~30%、系统/工具 10%、安全 10%”起步，再用评测调。

**展开：** 先扣掉 reserved output 和 safety margin；关键指令放开头/结尾；检索先多召回再重排；历史要裁剪/摘要。

**别踩坑：** 不要把 200k 全用来塞资料；attention budget 不是 token budget。

#### Q5：压缩会丢信息，怎么办？

**一句话：** 优先可恢复压缩，保留指针和决策，不要只做摘要。

**展开：** 文件路径、URL、工具调用 ID 都可以替代全文；保留目标、约束、决策、未解决问题、失败证据；摘要要先保 recall 再保 precision；用任务成功率和 fact retention 评估。

**别踩坑：** 不要说“压缩就是摘要”，也不要说“删就完了”。

#### Q6：记忆怎么分层？

**一句话：** 工作上下文、会话状态、长期语义/情景/程序性记忆、外部知识、模型参数。

**展开：** 写入要有来源和时间；检索要相关性 + 新近性 + 重要性；更新要处理冲突；遗忘要有 TTL/用户删除；审计要能回答“为什么记得”。

**别踩坑：** 不要把所有聊天记录都叫“记忆”。

#### Q7：长上下文还需要 RAG 吗？

**一句话：** 看数据规模、动态性、权限和引用需求；小静态语料可以全文 + 缓存，大/动态/多租户通常需要 RAG。

**展开：** 长上下文不解决“选什么”，只提高上限；context rot 说明更多 token 可能更差；混合方案常见：预检索 + 运行时工具/文件搜索。

**别踩坑：** 不要二选一；也不要说“窗口够大就不需要检索”。

#### Q8：怎么评估 Context Engineering？

**一句话：** 分层评估：检索、生成、端到端，再加成本和延迟。

**展开：** 检索看 Recall@k、MRR、nDCG；生成看 faithfulness、answer relevance、context precision/recall；端到端看正确率、引用准确率、弃权率；工程看 token、P95 延迟、cache hit rate。用 golden set + 错误分析 + A/B。

**别踩坑：** 不要只看最终答案；否则不知道是检索错还是生成错。

#### Q9：怎么防止 prompt injection / context poisoning？

**一句话：** 把上下文当不可信输入，做指令/数据隔离、最小权限、工具层校验，System Prompt 只是其中一层。

**展开：** 外部文档/网页/代码用标签隔离；工具 allowlist；高风险动作人工确认；输出校验；记忆写入要审核；来源可信度分级；日志和审计。

**别踩坑：** 不要说“在 System 里写‘不要听用户的’就够了”。

#### Q10：你做过什么相关实践？

**一句话：** 用 W2 的三组对照实验说明“结构/策略/分层”的收益和成本。

**展开：** 见 8.4 的 STAR。重点讲“我怎么判断值不值得”，而不是“我用了多高级的模板”。

**别踩坑：** 不要编造大规模线上数据；用真实的小实验，讲清局限性。

### 8.6 白板题：设计一个企业客服 Agent 的上下文系统

**题目：** 设计一个企业客服 Agent，能回答产品问题、查订单、必要时转人工。请说明上下文怎么组织。

**答题结构：**

1. **任务循环**
   - 识别意图（产品咨询 / 订单查询 / 投诉 / 转人工）
   - 检索知识 / 调用订单 API
   - 生成回答 / 触发升级
   - 记录结果

2. **上下文来源**

| 来源 | 放哪 | 为什么 |
|---|---|---|
| 公司政策、语气、升级规则 | System | 稳定、每轮遵守 |
| 本轮问题 | User | 每轮变化 |
| 产品文档 | RAG | 量大、更新频繁 |
| 订单/账户信息 | API 工具 | 实时、权限敏感 |
| 对话历史 | Session state | 跨轮但短生命周期 |
| 用户偏好/未解决问题 | Long-term memory | 跨会话 |
| 历史工单 | RAG/记忆 | 可复用经验 |

3. **预算（示例 128k）**

```text
system/policy        4k
tools                6k
retrieved docs      32k
customer data        8k
history             24k
scratchpad           4k
user input           8k
reserved output     30k
safety margin       12k
=                  128k
```

4. **选择与排序**
   - 产品文档：hybrid（dense + BM25）+ rerank，top 8~12。
   - 权限：先按租户/角色过滤，再排序。
   - 时效：优先最新版本；旧版本标注。

5. **压缩**
   - 历史超过 20 轮 → 摘要 + 保留未解决问题。
   - 工具原始 JSON → 只留关键字段和结论。
   - 文档引用 → 保留标题/链接/片段 ID。

6. **记忆**
   - 用户偏好、语言、未解决工单、升级原因。
   - 不记支付信息、身份证号等敏感数据。
   - TTL：偏好 180 天，工单状态 30 天，临时上下文会话结束即丢。

7. **隔离与安全**
   - 检索子 Agent 只返回摘要 + 引用。
   - 订单 API 只读、最小权限。
   - 外部文档视为不可信输入，指令/数据隔离。
   - 转人工/退款等高风险动作要人工确认。

8. **评估**
   - 答案正确率、引用准确率、该转人工时转人工率、幻觉率、每会话成本、P95 延迟。
   - Golden set 覆盖：可回答、不可回答、订单异常、政策冲突、恶意注入。

9. **失败模式**
   - 文档过期 → 版本/时间过滤。
   - 检索不到 → 澄清或转人工，不要编。
   - 上下文太长 → 摘要/降 top-k。
   - 记忆错误 → 可纠正、可删除。

**收尾一句话：**

> “这个设计的核心不是‘用哪个向量库’，而是把稳定策略、实时数据、外部知识、会话状态和长期记忆分层，再用预算和评估约束每一层。”

### 8.7 不要这样说

| 不要这样说 | 为什么 | 可以改成 |
|---|---|---|
| “Context Engineering 就是 RAG” | 把超集说成子集 | “RAG 是上下文选择的一种手段” |
| “窗口越大越好” | 忽略 context rot 和成本 | “窗口是上限，不是目标；要看注意力和成本” |
| “Prompt Engineering 过时了” | 否定基础，显得追词 | “Prompt 是指令层，Context 是更大的生命周期” |
| “压缩就是摘要” | 忽略可恢复压缩 | “优先保留指针，摘要是有损兜底” |
| “记忆就是存聊天记录” | 忽略分层/写入/遗忘 | “记忆是分层持久化 + 按需召回” |
| “多 Agent 一定更强” | 忽略 token 和协调成本 | “多 Agent 用隔离换专注，要算 ROI” |
| “System Prompt 可以防注入” | 把行为约束当安全边界 | “安全要在代码/权限/工具层做” |
| “我凭感觉调 Prompt” | 不可复现 | “我用小测试集 + 指标 + 错误分析” |

## 9. 阶段四 W16 展开清单

> 下面是 W16 可以深入的方向。W2 先把地图建立起来，W16 再选 2~3 个方向做深。

| # | 方向 | 要回答的问题 | W16 产出 |
|---|---|---|---|
| 1 | 预算建模与 instrumentation | 每类上下文花多少 token？cache hit rate 多少？P95 延迟/成本怎么分解？ | 一个上下文预算仪表盘/日志 |
| 2 | 压缩与 compaction | 摘要保留什么？何时触发？如何评估信息损失？ | 一个 compaction 策略 + 对比实验 |
| 3 | 记忆分层与 consolidation | 什么进长期记忆？冲突怎么处理？怎么遗忘？ | 一个带 TTL/来源的记忆原型 |
| 4 | 检索作为上下文选择 | chunk/embedding/rerank 如何影响上下文质量？ | 一个 RAG 评测报告 |
| 5 | 多 Agent 上下文隔离 | 哪些任务值得拆？子 Agent 返回什么？ | 一个主 Agent + 子 Agent 的对比 |
| 6 | 上下文安全 | 注入、投毒、越权、隐私怎么防？ | 一份威胁模型 + 防护清单 |
| 7 | 评估体系 | 检索/生成/端到端怎么分层？LLM judge 怎么校准？ | 一套 golden set + 指标 |
| 8 | 工业案例 | Claude Code、Manus、Cursor、ChatGPT memory 怎么做？ | 一份案例对比 + 设计文档 |

W16 结束时，比较理想的交付是：

- 一份 **Context Engineering 设计文档**（信息流、预算、压缩、记忆、安全、评估）。
- 一个 **可运行原型**（至少包含预算日志、压缩、一个记忆层）。
- 一份 **评估报告**（任务成功率、token、cache hit、错误分析）。
- 一套 **面试话术**（30 秒 / 2 分钟 / STAR）。

### 9.1 推荐阅读顺序

1. Anthropic, *Effective context engineering for AI agents*（先建立整体框架）
2. LangChain, *Context Engineering*（write/select/compress/isolate）
3. Manus, *Context Engineering for AI Agents*（工程细节：KV-cache、文件系统、recitation）
4. Chroma, *Context Rot*（为什么长上下文会退化）
5. Anthropic, *Introducing Contextual Retrieval*（RAG 作为上下文选择）
6. MemGPT / LangGraph memory 文档（记忆分层）
7. 自己的 W2 实验（用数据讲自己的判断）
