> 对应任务：口述练习 ReAct / RAG / MCP / Transformer；录音回听，找逻辑不清的地方。
> 用法：每个主题先自己脱稿讲一遍并录音 → 回听 → 对照标准稿找卡壳点 →

## 使用方法

1. 手机录音，脱稿讲每个主题（Transformer 3 分钟，其余各 2 分钟）。

## 一、Transformer（3 分钟版）

> Transformer 是 2017 年《Attention Is All You Need》提出的架构，完全靠注意力
> 建模序列关系，抛弃了循环结构。数据流是：文本先分词变 token，查嵌入表变成
> 向量，加上位置编码，然后过 N 层相同的结构——每层是多头自注意力加前馈网络，
> 各自套残差连接和 LayerNorm。注意力负责 token 之间横向交换信息，FFN 负责每个
> 位置独立的纵向变换。最后线性层投影到词表，softmax 得到下一个 token 的分布。
>
> 它比 RNN 好在两点：第一，自注意力所有位置一次算完，训练能并行，RNN 必须按
> 时间步串行；第二，任意两个位置直接建立连接，路径长度 O(1)，长程依赖不会像
> RNN 那样逐步衰减。现代大模型都是 Decoder-only，用因果掩码一次算完训练，
> 位置编码也进化到 RoPE 这类相对位置方案。

**自检**：能边说边画出"嵌入→N×(注意力+FFN)→softmax"吗？残差和 LayerNorm 的位置对吗？
（出处：`01Agent/w1day01`、`w1day02`）

## 二、RAG（2 分钟版）

> RAG 就是开卷考试：模型参数里的知识是闭卷记忆，会过时、不能引用；RAG 在推理
> 前从外部知识库检索资料放进上下文，让模型带着证据回答。它有两条流水线：离线
> 索引是文档→解析→切分→向量化→存进向量库；在线查询是问题→召回→融合→重排→
> 打包进上下文→生成带引用的回答。
>
> 几个关键决策：切分用递归字符切分保语义边界，200 到 800 token，重叠 10% 到
> 20%；检索用混合检索，因为向量检索强在同义改写、BM25 强在错误码这类精确词，
> 两路结果用 RRF 按排名融合，k 取 60；候选再用 cross-encoder 重排，因为交叉
> 编码器让问题和文档互相看见，排序更准。评估要分层：Context Recall 看检索漏
> 没漏，Context Precision 看排序，Faithfulness 看答案是否被资料支持——排查
> 顺序永远是先检索后生成。
>
> 我自己跑过全套实验：15 篇文档、15 题黄金集，混合检索把 Recall@5 从 0.867
> 提到 0.933，重排把 MRR 从 0.639 提到 0.717。另外，不是什么场景都要 RAG——
> 知识库小而静态、或者缺的是推理不是知识的时候，直接放上下文或用工具更好。

**自检**：两条流水线的每一步能一口气说完吗？能引用自己实验的数字吗？
（出处：`01Agent/w3day03~06` 各报告）

## 三、ReAct 与 Function Calling（2 分钟版）

> ReAct 是 Agent 的基础循环：Thought 想清楚还缺什么，Action 决定调哪个工具，
> Observation 把工具的真实结果拼回上下文，循环到 Final Answer。它比纯推理强在
> 把不确定的部分外包给真实工具，推理从凭记忆变成凭证据。我手写过完整循环：
> 协议写在 system prompt 里，模型输出结构化文本，代码正则解析执行——文本协议
> 可用但脆弱，偶尔格式违规要重试提示。
>
> Function Calling 是同一条链路的协议版：工具的 JSON Schema 挂在请求体 tools
> 字段，模型返回 tool_calls 对象而不是自由文本，字段由协议保证。完整四步是：
> 定义工具、模型决策、代码执行、role=tool 回传结果，模型再生成最终回答。
> 主循环盯着 finish_reason：tool_calls 表示继续，stop 表示结束。模型只是产出
> 调用意图，真正执行工具的永远是代码——所以说 Function Calling 是 Agent 的手。
> 并行调用时模型一条消息给多个 tool_calls，客户端并发执行后一次性回传，
> 墙钟时间从求和变成取最大。

**自检**：四步能边说边写请求体形状吗？tool_call_id 配对规则说得清吗？
（出处：`01Agent/w4day01~03`）

## 四、MCP（2 分钟版）

> MCP 是 Anthropic 开源的模型上下文协议，一句话：工具生态里的 USB——写一次
> MCP Server，任何支持 MCP 的客户端都能用。没有 MCP 是 M 个应用乘 N 个数据源
> 份胶水代码，有了 MCP 变成 M+N 份实现。
>
> 三层角色：Host 是用户直接用的宿主应用，管鉴权和用户确认，是安全边界；
> Client 在 Host 内部和每个 Server 保持一对一连接，负责握手和转发；Server 是
> 暴露能力的轻量进程，可以提供 Tools（模型可调用的函数）、Resources（只读
> 数据）和 Prompts（提示模板）。传输上本地走 stdio 的 JSON-RPC 2.0，我按官方
> SDK 写过一个 Server，用最小客户端做端到端测试：拉起子进程、initialize 握手、
> tools/list 发现、tools/call 调用，9 项检查全过。
>
> MCP 和 Function Calling 不冲突：MCP Server 列出的工具，最终还是通过 Function
> Calling 让模型决策调用。单应用内部直接 FC 最简单；要接生态、跨应用复用、
> 把集成能力分发给用户，用 MCP。

**自检**：三层角色各自职责不打架吗？"M+N"相对什么说的能讲清吗？
（出处：`01Agent/w4day04`、`w4day05`）

## 五、Prompt → Context Engineering（1 分钟，面试加分项）

> 这两年面试话术从 Prompt Engineering 升级成了 Context Engineering：以前管
> "一条提示词怎么写"，现在管"整个上下文窗口里放什么"。三个核心问题：预算
> ——窗口、注意力质量、成本延迟一起算，不是越大越好；压缩——优先可恢复
> 压缩（保留路径、URL、ID 这些能取回原文的引用），摘要是有损兜底；记忆分层
> ——工作上下文、会话状态、长期记忆、外部知识、模型参数，各归各的工具管。
> 从这个视角看，RAG 的检索、排序、去重，本质都是在做上下文的选材和排版。

（出处：`01Agent/w2day06` 的 Context Engineering 笔记）
