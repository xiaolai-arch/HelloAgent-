# RAG 两条流水线：索引与查询

## 一句话理解

RAG = 开卷考试：先从外部知识库找到相关资料，再把资料放进上下文，让模型带着证据回答。模型参数里的知识是闭卷记忆：有截止日期、会过时、无法引用。RAG 是外部记忆：可更新、可引用、可审计。

## 离线索引流水线（Ingestion）

```text
文档 → 解析 → 清洗 → 切分 → 元数据 → 向量化 → 向量索引
```

每一步的关键决策：解析要不要保留版面和表格；清洗去多少噪声；切分的大小、重叠和边界；元数据带不带来源/章节/时间/权限；用什么 Embedding 模型；选什么向量索引。离线做不好，在线怎么调都没用——很多"检索不准"的根因在 PDF 解析或切分边界，不在模型。

## 在线查询流水线（Query）

```text
问题 → 改写 → 召回(Dense+Sparse) → 融合 → 重排 → 上下文打包 → 生成 → 引用
```

召回阶段先取较多候选（如 20~100 条），重排后取 5~20 条进入上下文。打包时去重、按相关性排序、控制 token 预算、加引用编号，并用 `<context>` 之类的标签把资料和指令隔开。生成要求"只根据资料回答、带引用编号、资料不足明确说不知道"。

## Chunking 策略与经验参数

- **固定长度切分**：每 N 个 token 切一刀，带 overlap。最快，但容易把句子和表格拦腰切断。
- **递归字符切分**：先按段落、再按句子、最后按字符逐级回退，尽量保持语义完整，是通用默认选择。
- **语义切分**：用 Embedding 相似度找主题边界，效果好但成本高。
- **结构感知切分**：按 Markdown 标题、代码函数边界切，适合技术文档。

经验区间（不是定律）：chunk 大小 200~800 token 起步，事实问答偏小、长文推理偏大；overlap 取 10%~20%；表格、代码、公式尽量保持完整；每个 chunk 带上 title、section、source 元数据。

## 什么时候不需要 RAG

知识库小且静态（能整体放进上下文）、任务缺的是推理而不是知识、数据结构化且查询明确（用 SQL/API）、延迟极度敏感——这些场景都不该上 RAG。先问：模型缺的是知识、推理、权限，还是实时性？
