# 向量数据库：存向量、找近邻

## 解决什么问题

RAG 需要在一个几万到几亿条的向量库里快速找出"和查询向量最相近的 k 条"。暴力遍历算余弦是 O(N·d)，库大了扛不住。向量数据库用 ANN（Approximate Nearest Neighbor，近似最近邻）索引换速度：允许极小的召回损失，换取几个数量级的提速。最常用的索引是 HNSW（分层可导航小世界图）：建多层图，查询时从顶层粗定位、逐层细化，复杂度近似 O(log N)。

## CRUD 概念（以 Chroma 为例）

向量数据库的核心操作就四个：

- **Create**：建 Collection（集合，类似关系库的表），指定距离度量（余弦/L2/内积）。
- **Insert（add/upsert）**：写入向量 + 原文 + 元数据（metadata，如来源、章节、时间、权限标签）。upsert 按 ID 存在则更新、不存在则插入。
- **Search（query）**：给查询向量（或文本），返回 top-k 及其相似度分数；可以叠加 metadata 过滤（where 条件）。
- **Delete/Update**：按 ID 删除或更新。

元数据过滤在生产里极其重要：权限隔离（这个用户能看哪些文档）、时间范围（只用最近版本）、文档类型，都应该在检索层过滤，而不是检索完再丢掉。

## 选型速查

- **Chroma**：最轻量，pip 安装即用，默认持久化到本地目录，适合入门和小项目。
- **FAISS**：Meta 出的库不是服务，最快最灵活，但要自己管持久化和元数据。
- **Qdrant**：Rust 写的，过滤和混合检索好，有云服务，生产化好。
- **pgvector**：PostgreSQL 插件，事务和权限直接复用 PG 生态。
- **Milvus**：分布式，面向大规模。

选型不要只看速度：元数据过滤、ACL、增量更新、备份、可观测性、运维成本同样重要。
