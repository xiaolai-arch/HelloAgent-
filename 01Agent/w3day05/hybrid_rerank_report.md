## 一、BM25 vs Dense：强弱互补

| 维度 | BM25（稀疏） | 向量（稠密） |
|---|---|---|
| 原理 | 词频 × 逆文档频率（词面匹配） | 语义空间余弦（意思匹配） |
| 强项 | 精确词：错误码/型号/人名；可解释；零成本 | 同义改写、跨语言、口语化问法 |
| 弱项 | 换个说法就找不到 | 精确词被语义平滑；需要编码模型 |
| 本实验实现 | 手写 Okapi BM25（k1=1.5, b=0.75，中文 bigram） | bge-small-zh + Chroma |

BM25 公式（手写实现逐项注释见脚本）：

```text
score(q,d) = Σ IDF(t) · tf·(k1+1) / (tf + k1·(1-b+b·|d|/avgdl))
IDF(t) = log((N - df + 0.5) / (df + 0.5) + 1)
```

## 三、单题解剖

### 精确词题 Q9：报销系统报错 TRV-40907 应该怎么处理？

- dense top3：['15_helloai_policy#c4', '09_rag_eval#c5', '15_helloai_policy#c0']
- bm25  top3：['15_helloai_policy#c4', '15_helloai_policy#c5', '15_helloai_policy#c3']
- 看第 2、3 名的差异：BM25 的 top3 全是差旅制度文档的 chunk（错误码、
  报销期限等字面强相关），dense 的第 2 名却混进了 RAG 评估文档——
  在语义向量眼里"报销系统报错"和"评估/错误分析"的向量距离也不算远。
  TRV-40907 这种字面锚点，正是 BM25 的主场。

### 多跳题（Day3 的两道 MISS：Q11/Q12）

- Q12：dense miss → 重排后 top5 ['13_mcp#c4', '12_react_function_calling#c2', '12_react_function_calling#c3', '13_mcp#c2', '12_react_function_calling#c1']（命中 [0, 1, 0, 0, 0]）——MCP 文档和 FC 文档的 chunk 分居两路召回，融合进候选后由重排捞回 top5。
- Q11：仍然 miss（dense 命中 [0, 0, 0, 0, 0]，重排 [0, 0, 0, 0, 0]）。它的三个 gold 关键词（提前 3 个工作日 / 600 元 / 100 元餐补）被切进了不同 chunk，任何单个 chunk 都凑不满 2 个命中——这是 Day4 实证过的"切分散信息"问题，检索和重排都救不了，要靠父子块或更粗的切分粒度。
- 多跳困难是"信息住不同 chunk"：混合检索提供更多样的候选（两路互补），
  重排把分散在两路里的相关块捞上来——这正是漏斗设计的意义；但候选里
  凑不齐信息的题，只能回切分层去修。

## 四、Rerank 的账：收益 vs 延迟

- 重排 15 题 × 20 候选共 45.9s（cross-encoder，本地推理）。
- 它解决的是"排序"：相关块在候选里但排不进 top5 时，cross-encoder 因为
  让 query 和 chunk 在模型内部互相看见，能把它们捞上来。
- 它解决不了"召回"：候选 20 条里根本没有相关块，重排也无能为力——
  所以是"宽召回 → 精排"的漏斗，而不是"小召回 → 精排"。

## 五、结论

1. **混合检索值回票价**：hybrid_rrf 的 Recall@5=0.933 / MRR=0.639，对比纯 dense 0.867/0.606、纯 BM25 0.8/0.65——两路的强项题（语义改写 vs 精确词）几乎不重叠，融合后互为补丁。
2. **重排再抬一层**：MRR 0.639 → 0.717，代价是每题多 3.06s 延迟。生产上 rerank 是最常用的 "最后一公里"优化，但永远排在"把召回做好"之后。
3. **RRF 为什么稳**：只看排名不看分数（k=60），
   BM25 的分数量纲和余弦不同没法直接加；排名是无量纲的，融合无需求归一化。
4. **单路都有死穴**：dense 输精确词题、BM25 输改写题——看你业务里
   哪类问题多，但多数生产 RAG 直接默认 hybrid。
